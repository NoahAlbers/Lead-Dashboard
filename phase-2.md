1. The Lead Console (this repo)
2. The intake form at https://github.com/NoahAlbers/acb-form (acb-intake-form.html)

Read this entire plan before writing any code. Plan the implementation, then build the Lead Console side first, then provide the form-side changes as a separate deliverable.

## ARCHITECTURE OVERVIEW

The goal is ZERO lead loss between form submission and the Lead Console. Every lead must be captured, confirmed, and verifiable. The system uses 6 layers of protection:

1. Partial lead capture (save contact info before form is fully completed)
2. Direct API submission with confirmation receipt
3. FormSubmit.co as a backup fallback
4. Write-ahead ingestion queue (raw payload saved before any processing)
5. Health monitoring (form knows if the API is reachable)
6. Reconciliation (detect any gaps)

```json
    "form_started_at": "ISO timestamp when user began filling form",
    "form_completed_at": "ISO timestamp when user clicked submit"
  }

```

Response on success (200):
```json
{
  "success": true,
  "receipt_id": "ACB-2026-0001",
  "lead_id": "uuid",
  "submission_id": "uuid-echoed-back",
  "received_at": "ISO timestamp",
  "status": "received"
}
```

Response on duplicate submission_id (200, not error):
```json
{
  "success": true,
  "receipt_id": "ACB-2026-0001",
  "lead_id": "uuid",
  "submission_id": "uuid",
  "status": "already_received",
  "message": "This submission was already processed"
}
```

Response on validation error (400):
```json
{
  "success": false,
  "error": "validation_error",
  "message": "Missing required fields",
  "missing_fields": ["email"]
}
```

Response on server error (500):
```json
{
  "success": false,
  "error": "server_error",
  "message": "Internal error — submission may not have been saved"
}
```

CRITICAL behaviors:
- This endpoint must be PUBLIC (no auth required — it's called from the public form)
- Protect with rate limiting: max 10 submissions per IP per minute
- Protect with a simple API key or shared secret passed in a header (X-ACB-Form-Key) that the form includes — not bulletproof security, but prevents random POSTs
- CORS must allow the form's GitHub Pages origin AND the Webflow domain
- The FIRST thing the endpoint does is write the raw payload to the ingestion_queue table — BEFORE any validation, scoring, or processing. This ensures the data is saved even if downstream processing fails.

### New API Endpoint: POST /api/leads/partial

Same structure as /api/leads/ingest but with `is_partial: true` and `partial_step` indicating which step was completed (e.g., "contact_info", "portfolio_details", "collections_readiness").

Behavior:
- If a partial record with this session_id already exists, UPDATE it with the new fields (merge, don't overwrite — add new fields to existing ones)
- If no record exists, CREATE a new partial record
- Partial leads are stored in the same ingestion_queue table with status "partial"
- When a full submission arrives with the same session_id, the partial record is upgraded to a full submission and processed normally
- Partial leads that are never completed should be visible in the Lead Console after a configurable timeout (default: 1 hour) with a "Partial — Incomplete" status

### New API Endpoint: GET /api/health

Public, no auth. Returns:
```json
{
  "status": "ok",
  "timestamp": "ISO",
  "database": "connected",
  "queue_depth": 0,
  "last_lead_received_at": "ISO timestamp"
}
```

If database is unreachable: `{ "status": "degraded", "database": "disconnected" }`
This endpoint should respond in <200ms. The form checks this before enabling the submit button.

### New Database Table: ingestion_queue

This is the write-ahead log. Every submission lands here first.

| Field | Type | Description |
|---|---|---|
| id | uuid | Primary key |
| submission_id | uuid | Unique ID generated by the form (for dedup) |
| session_id | uuid | Browser session ID (links partials to finals) |
| status | string | received, partial, processing, completed, failed, duplicate |
| is_partial | boolean | |
| partial_step | string (nullable) | Which step was last completed |
| raw_payload | jsonb | The ENTIRE request body, unmodified |
| lead_id | uuid (nullable) | FK to leads table — populated after processing |
| receipt_id | string (nullable) | Human-readable receipt (ACB-2026-XXXX) |
| form_version | string | |
| source_ip | string (nullable) | |
| error_message | text (nullable) | If processing failed, why |
| retry_count | integer | Default 0 |
| received_at | timestamp | When the API received the request |
| processed_at | timestamp (nullable) | When processing completed |
| created_at | timestamp | |
| updated_at | timestamp | |

Indexes:
- UNIQUE on submission_id (prevents duplicate processing)
- Index on session_id (for linking partials to finals)
- Index on status (for queue processing)

### Receipt ID Generation

Receipt IDs should be human-readable and sequential:
- Format: ACB-{YEAR}-{SEQUENTIAL_NUMBER}
- Example: ACB-2026-0001, ACB-2026-0002, etc.
- Reset numbering annually or use a global counter
- Store in a simple sequence table or use a database sequence

### Ingestion Processing Pipeline

After writing to ingestion_queue, process the lead asynchronously (can be immediate or via background job):

1. **Validate** — Check required fields (email OR phone must be present). Log validation errors but still keep the record.
2. **Deduplicate** — Check if a lead with this email+phone+company already exists. If so, flag as duplicate but still create the record (don't silently discard).
3. **Normalize** — Parse multi-select fields into arrays, normalize state names, trim whitespace, standardize phone format.
4. **Create Lead** — Insert into the leads table with all fields mapped.
5. **Score** — Run the scoring engine.
6. **Referral Check** — Run referral matching.
7. **Update Queue** — Set ingestion_queue status to "completed", link lead_id.
8. **Notify** — Fire new lead notification (Feature 5 from the previous PRD).

If ANY step after validation fails:
- Set ingestion_queue status to "failed" with error_message
- The raw payload is PRESERVED — nothing is lost
- Retry up to 3 times with exponential backoff
- After 3 failures, flag for manual review

### Partial Lead Handling

After 1 hour (configurable in admin settings), partial leads that were never completed should:
1. Be created as actual leads with status "Partial — Incomplete"
2. Have whatever fields were captured (at minimum: contact info)
3. Be scored (will likely score low due to missing data)
4. Appear in the Lead Inbox with a distinct "Partial" status badge (orange/gray)
5. Be assignable and contactable like any other lead
6. Include a note: "This lead started the intake form but did not complete it. Last step completed: [step name]"

Add a default saved view: "Incomplete Submissions" that filters to partial leads.

Add a new section to the Admin Settings or Reports page: "Ingestion Health"

## FORM-SIDE CHANGES (acb-intake-form.html)

Generate these changes as a SEPARATE file or clear instructions so they can be applied to the form repo.

### On Form Load

When the form page loads:
1. Generate a `session_id` (UUID v4) and store in memory (not localStorage — fresh per page load)
2. Capture metadata: referrer, UTM params from URL, user agent, page URL
3. Record `form_started_at` timestamp
4. Ping `GET /api/health` on the Lead Console — store result. If unreachable, form still works (will fall back to FormSubmit.co only)

### On Contact Info Step Completion

When the user completes the step that has name, email, phone, and company (and clicks "Next"):
1. Generate a `submission_id` for the partial (UUID v4, distinct from the final submission_id)
2. Fire a background POST to `/api/leads/partial`:
```json
   {
     "submission_id": "<partial-uuid>",
     "session_id": "<session-uuid>",
     "is_partial": true,
     "partial_step": "contact_info",
     "fields": {
       "first_name": "...",
       "last_name": "...",
       "email": "...",
       "phone": "...",
       "company_name": "..."
     },
     "metadata": { ... }
   }
```
3. This fires silently — do NOT block the user or show any loading state
4. If it fails, log to console but do nothing visible — this is a best-effort safety net

### On Each Subsequent Step Completion

Fire another background POST to `/api/leads/partial` with the same session_id, updated partial_step, and ALL fields collected so far (cumulative). The Lead Console merges them.

### On Final Form Submission

This is the critical path. The submission logic should be:
```javascript
async function submitForm(formData) {
  const submissionId = generateUUID();
  const payload = {
    submission_id: submissionId,
    session_id: sessionId,
    submitted_at: new Date().toISOString(),
    form_version: "1.0",
    is_partial: false,
    partial_step: null,
    fields: { ...formData },
    metadata: { ...collectedMetadata, form_completed_at: new Date().toISOString() }
  };

  // ATTEMPT 1: Direct API submission
  try {
    const response = await fetch(LEAD_CONSOLE_API + '/api/leads/ingest', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-ACB-Form-Key': FORM_API_KEY
      },
      body: JSON.stringify(payload)
    });

    if (response.ok) {
      const result = await response.json();
      // SUCCESS — show confirmation with receipt ID
      showSuccess(result.receipt_id);
      return;
    }

    // Response not OK — try retry
    throw new Error(`API returned ${response.status}`);

  } catch (error) {
    console.error('Primary submission failed:', error);

    // ATTEMPT 2: Retry once after 2 seconds
    try {
      await new Promise(r => setTimeout(r, 2000));
      const retryResponse = await fetch(LEAD_CONSOLE_API + '/api/leads/ingest', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'X-ACB-Form-Key': FORM_API_KEY
        },
        body: JSON.stringify(payload)
      });

      if (retryResponse.ok) {
        const result = await retryResponse.json();
        showSuccess(result.receipt_id);
        return;
      }
      throw new Error(`Retry failed: ${retryResponse.status}`);

    } catch (retryError) {
      console.error('Retry failed:', retryError);

      // ATTEMPT 3: FormSubmit.co backup
      try {
        await submitToFormSubmit(formData);
        // Show success WITHOUT receipt ID (since we don't have one)
        showSuccess(null, true); // true = backup mode
        return;

      } catch (backupError) {
        console.error('Backup submission also failed:', backupError);
        // LAST RESORT: Show error with the user's data so they can contact us manually
        showFailureWithData(formData);
      }
    }
  }
}
```

## RECONCILIATION SYSTEM (Lead Console)

### Daily Reconciliation Job

Build a background job that runs daily at midnight EST:

1. Count submissions received in the last 24 hours (from ingestion_queue)
2. Count leads created in the last 24 hours (from leads table)
3. Count failed/stuck submissions (ingestion_queue status = failed or processing for >10 minutes)
4. If any submissions are in "received" or "processing" state for >10 minutes, re-process them
5. Log a reconciliation report to a new `reconciliation_logs` table
6. If any discrepancy (submissions received > leads created + known duplicates + known failures), fire a critical notification to admins: "Lead ingestion discrepancy detected: X submissions received but only Y leads created"

### Reconciliation Dashboard Widget

Add to the Admin Settings ingestion health page:
- Last reconciliation run timestamp
- Result: "All clear — 12 submissions, 12 leads created" or "⚠ Discrepancy — 12 submissions, 10 leads created, 1 duplicate, 1 missing"
- Manual "Run Reconciliation Now" button
